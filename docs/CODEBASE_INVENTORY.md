# Darbak Codebase Inventory

Generated by reading the code on branch `refactor/location-selection`, 2026-09-06. This is a
snapshot, not a living document — re-derive it after significant refactors rather than trusting it
blindly. Facts here were established by `grep`/`read`, not by running the app; anything requiring a
device or a live network response is called out in §6.

The `lib/modules/location/` module (region & branch selection) is deliberately **not** covered here
in depth — it is documented in `specs/001-region-branch-selection/`.

---

## 1. Module Map

Each entry: feature, entry point + route, cubits + state, endpoints called, module dependencies.

### `auth/signin`
Sign-in screen and its bloc. Entry: `SignInScreen` (`presentation/pages/signin_screen.dart`), route
`/signin` (`Routes.signin`) — also embedded inline (not via the router) from other auth screens and
from `search_Screen.dart`'s guest-login bottom sheet, in `SignInMode.gate` vs `SignInMode.entry`
modes (see CLAUDE.md's Authentication Flow section). `SignInBloc` (a `Bloc`, not a `Cubit` — the one
exception in the codebase) holds sign-in form/request state; `AuthStatusCubit` (global, in
`auth/blocs/`) holds the tri-state signed-in/guest/loading flag read by Profile and Bookings.
Endpoint: `POST /login`. Depends on: `home/selectLanguage` (locale), `core` (SharedPreferences,
Dio), and is depended on by nearly every other module transitively via `AuthStatusCubit`/`requireAuth`.

### `auth/register`
Registration + OTP verification. Entry: `RegisterPage` (`presentaion/pages/register_page.dart`) —
reached only by direct widget embedding from `signin_screen.dart` and `login_noAuth.dart`, never via
`context.pushNamed(Routes.register)` (see §3, DEAD). `RegisterCubit` holds registration form state.
`OtpVerifyScreen` (route `/otp`, live) verifies the code. Endpoints: `POST /register`
(multipart, via `package:http`), `POST /register/verify`, `POST /register/resend-otp` (both hit
directly in `otp_register.dart` with `package:http`, bypassing `RegisterCubit`/the datasource).

### `auth/forgotPassword`
Password-reset wizard. Entry class is `ForgotPasswordScreen` in
`presentaion/widgets/forgotPassword.dart` (an odd location for a screen — it's under `widgets/`).
Reached only via `ForgotPasswordScreen.entry()` embedded inline from `signin_screen.dart` and
`register_page.dart`; the GoRoute `/forgot-password` has zero push sites (DEAD, see §3). The whole
wizard (phone entry → `EnterCodeScrean` → `ChangePasswordScreen` → a `successPage.dart`) is driven by
`showModalBottomSheet`/inline `child:` swaps, not by navigation — `EnterCodeScrean` and
`ChangePasswordScreen`'s own GoRoutes (`/enter-code`, `/change-password`) are likewise DEAD.
`ForgetPasswordCubit` holds the flow's state across all three steps. Endpoints: `POST
/password/forget`, `POST /password/code`, `POST /password/reset` (all via `package:http`).

### `auth/on_boarding`
Single-file, three-page swipe intro (`OnBoarding`, route `/onboarding`, reached via
`context.go('/onboarding')` string literals from splash and language-select, never via
`Routes.onBoarding` named push). No cubit; writes `hasSeenOnboarding` to SharedPreferences directly
and calls `context.go('/home')` on finish/skip. No module dependencies beyond core.

### `auth` (splash + status, no subfolder)
`SplashScreenOld` (`splash_screen.dart`, route `/`, `initialLocation`) is the sole auth gate —
see CLAUDE.md's Authentication Flow section for its priority order. `AuthStatusCubit`
(`blocs/auth_status_cubit.dart`, global lazy singleton) is the only cross-module read: it emits
`true` only when a non-empty token exists, `false` for guests and logged-out. No direct endpoint
calls of its own (reads the token from `SharedPreferencesHelper`).

### `home/home_screen`
One file (`clasic.dart`), class `Clasic` — the live daily-rent entry, reached from
`search_Screen.dart` via `Routes.classic`. Provides a screen-scoped `LocationSelectionCubit`
(`registerFactory`) and renders `DailyRentBody` (in `booking_packages/widgets/`). No endpoints of
its own; delegates region/branch selection to the location module and pushes
`Routes.carsListPackage` with a `FilterModel` once a branch + dates are chosen.

### `home/booking_packages`
Five "pick a rental type" screens sharing one shape: `DailyPackages` (`ui/daily_package_screen.dart`
— dead route `/daily-package`, see §3), `MonthlyPackageScreen`, `AirportPackageScreen`,
`DeliveryPackageScreen` (all live, each with a screen-scoped `LocationSelectionCubit`), plus
`CarsListPackage`/`CarsMonthlyScreen` (the intermediate car-list screens these four push into,
carrying a `FilterModel`). No cubit of its own beyond the shared `LocationSelectionCubit`/`SearchCubit`
(date/time picking, out of the location rewrite's scope). Endpoints: none directly — calls
`CarsCubit.getAllCars` (see `home/cars`) once a branch is picked. Depends on: `location`,
`home/search_screen` (`SearchCubit`, `FilterModel`), `home/cars` (`CarsCubit`), `home/profile`
(`ProfileCubit.custClass`).

### `home/booking_from_cars`
The "book this specific car" flow. Entry: `BranchWithCarScreen` (`presentaion/view/branchs_with_car_screan.dart`),
route `/branch-with-car`, pushed from `cars_info.dart`. Provides a screen-scoped
`LocationSelectionCubit` started with `LocationFilter.car(carId)` (no region step — see the
location spec). No cubit of its own since this session's Phase 8 deletion removed the legacy
`BookingFromCarsCubit`/its state/remote datasource/model entirely; the folder now holds only the
screen, `branches_card.dart` (the "delivery" promo card on the home hero, oddly named — its `onTap`
pushes `Routes.deliveryPackage`), and `branchs.dart` (a plain `BranchTile` display widget). No direct
endpoints (branch data comes from `LocationRepository`). Builds a `BookingDraft` and pushes
`Routes.additions`.

### `home/search_screen`
The Home tab (`SearchScreen`, `presentaion/search_Screen.dart`, route `/home`, shell branch 0) plus
`SearchCubit` (global lazy singleton) — the largest shared cubit in the app, mixing date/time/rent-type
state (still live, out of the location rewrite's scope) with `getOffers`/`getRegions`/`getAreas`
methods, an `AreasModel` sub-flow, and the `selectedReceiveModel`/`selectedDriveModel` bridge fields
every booking flow writes before validating (see CLAUDE.md's Selection Persistence section).
Endpoints: `GET /regions`, `GET /areas`, `GET /check_for_offers` (via `offers_remte_datasource.dart`,
`package:http`), `POST /available/time` (`check_date_remote.dart`, validates a booking's dates —
the final authority per the location constitution's Principle IV). Also home to the now-orphaned
"areas" selection widgets (`areas_list_view.dart`, `region_tile.dart`'s sibling `AreasListView`) —
see §5, this widget lost its only caller in this session's location-module deletion pass and its
own `element.name == ...` lookup is a live, un-migrated Principle I violation. Depends on: `location`
(hero-panel prefetch only), `home/cars`, `home/profile`.

### `home/cars`
Car listing, filtering, and detail. Entries: `AllCarsScreen` (route `/cars`, also shell branch 1
`/fleet`), `CarsInformation` (route `/car`, the single place a `BookingDraft` is built for four of
the five booking flows — see the location spec's Phase 7 notes), `FiltersCars` (`/filter-cars`),
`SearchCarScreen` (`/search-cars`), `ImageCarPage` (`/car-images`). Cubits: `CarsCubit`
(`registerFactory`, per-screen car list + pagination), `AllCarsCubit` (`registerFactory`, the
`/fleet` tab and general car search — including the `legacyCarSearchUrl` bare-domain search, flagged
`TODO(backend)` in `api_path.dart`), `FilterCubit` (`registerLazySingleton` — filter selections,
shared across the fleet + filter screens). Endpoints: `GET /cars/filter` (`cars_remote_datasource.dart`,
also used for the branch-scoped and paginated variants via query params), `GET /manufactories`,
`GET /web/manufactories`, `POST /favorite/{carId}` (favouriting), `GET {legacyCarSearchUrl}` (the
flagged legacy-domain search, bypasses `AppInterceptors`). Depends on: `home/booking_packages`,
`home/booking_from_cars`, `home/additions`, `home/profile` (`custClass`).

### `home/additions`
Add-ons (extras) step between branch/date selection and payment. Entry: `AdditionsScreen`
(`presentaion/pages/additions_screen.dart`, route `/additions`). `AdditionsCubit` (registered
`registerFactory` but provided exactly once, globally, at `bloc_providers.dart:27` — behaves as an
app-lifetime singleton, see §5) holds the selected add-ons, running total, and the fetched
`StepOneOrderModel`. `getCarFeatures` builds the `POST /orders/step1` body from a `BookingDraft`
(see the location spec's Phase 7). `checkOrderStep` hits `checkSteps`/`orders/check`. Also embeds
`PaymentMethodsScreen` and cashback (`CashbackRemoteDataSource`/`ApplyCashbackRemoteDataSource`,
each constructed with a **bare `Dio()`**, see §5) directly as `child:` widgets rather than via
routing. Endpoints: `POST /orders/step1`, `POST /contracts/step1` (the parallel "automation" path,
apparently unreachable — see §5/§6), `GET/POST /orders/check`. Depends on: `location`
(`BookingDraft`), `home/payment`, `home/cash_back`.

### `home/payment`
Payment method selection and the invoice/confirmation screens. Entries: `PaymentMethodsScreen`
(route `/payment-methods` — DEAD as a named route, reached only by direct embedding from
`additions_screen.dart`, see §3), `InvoiceUI` (`/invoice` — the other confirmed-dead route),
`InvoiceNotCompletedUI` (`/invoice-not-completed` — also DEAD as a route, reached only via
`PersistentNavBarNavigator.pushNewScreen`), `WebPayment` (`/web-payment`, live, opens Apple Pay /
card 3-D-Secure redirect URLs). `InvoiceCubit` (registered `registerFactory` but, like
`AdditionsCubit`, provided once globally at `bloc_providers.dart:28` — behaves as a singleton, §5)
wraps `InvoiceRepository`/`PaymentRepository`/`CouponRepository`. Endpoints: `POST /orders/step2`
(invoice), `POST /orders/step3` (payment), `POST /order/coupon`, `POST /order/delete-coupon`,
`GET /order/coupons`, `POST /order/points`, `POST /order/delete-points`, `GET /available/time`
(re-validated here too), plus the oracle-domain `GET {oracleApi}/customerSync/{idNumber}` (loyalty
points, called from `points_tile.dart` with a **bare `Dio()`**). Depends on: `home/all_bookings`
(booking-confirmed navigation), `home/cash_back`.

### `home/booking_confirmed`
One file, one bottom-sheet screen (`BookingConfirmedBottomSheet`), route `/booking-confirmed`
(rendered via `BottomSheetPage`, a custom transition — see `core/router/bottom_sheet_page.dart`).
No cubit, no endpoint of its own; navigates to `/bookings` or `/home` on its two buttons.

### `home/all_bookings`
The Bookings tab (`AllBookingScreen`, shell branch 2 `/bookings`) with three sub-tabs: running,
previous, and not-completed orders. `AllBookingCubit` is registered `registerFactory` but provided
once globally at `bloc_providers.dart:30` (behaves as a singleton, §5) **and** a second, separate
instance is constructed inline inside `AdditionsCubit`'s own DI registration
(`AdditionsCubit(sl(), sl(), AllBookingCubit(sl(), sl()), sl())` in `service_locator.dart:79`) —
that second instance is held as a field (`allBookingCubit`) but **no method is ever called on it**
anywhere in `additions_cubit.dart` (verified by grep) — dead weight constructed on every
`AdditionsCubit` build. `BookingAutomationCubit` exists for a parallel "automated/contract" booking
type that appears structurally unreachable (see §5/§6, `RentType.automated` is never set). Entry for
a single booking's detail: `BookDetails` (route `/book-details`). Endpoints: `GET
/orders/get-orders`, `PUT /order/cancel`, `POST /orders/delete-order`, and the automation-path
equivalents (`/contracts`, `/cancel/contracts`). Depends on: `home/payment`, `home/cars`.

### `home/all_branching`
Legacy "browse all branches" screen, **not** part of the location-selection rewrite's booking flow.
`BranchesScreen` (route `/branches`, live, reached from the Profile tab) was converted in this
session's Phase 8 from `AllBranchCubit` onto `LocationRepository` directly (no cubit — a local
`_LoadState` enum + `setState`). The module's own `BranchRepository`/`AllBranchRemoteDataSource`
(`GET {mainApi}/branches?perPage=60`)/`BranchLocalDataSource` (the `branches_box` Hive box) survive
in `service_locator.dart` but are now **fully orphaned** — their only consumer, `AllBranchCubit`, was
deleted this session and nothing else calls `BranchRepository.getBranches()` (see §5). `branch_model.dart`
still defines the old `BranchModel`/`WorkTime`/`Alldays`/`Fri`/`Mon`/`Afternone`/`PolygonPoint`/
`BranchCenter`/`Data`/`Links`/`Meta`/`Link` classes — `BranchModel` itself stays live as the id/name
bridge type `SearchCubit.selectedReceiveModel`/`selectedDriveModel` hold; the rest are referenced
only by the now-orphaned `BranchRepository` chain. `ViewLocation` (route `/view-location` — DEAD as
a named route, reached only via `PersistentNavBarNavigator.pushNewScreen` from `branches_screen.dart`)
also lives here despite the folder's name suggesting it's branch-list-only.

### `home/profile`
The Profile tab (`MyProfile`, `page/profile.dart`, shell branch 3 `/profile`) plus a cluster of
sub-features under `page/`: `edit_profile` (`EditProfileCubit`, `POST /profile` multipart via
`package:http`), `reset_password` (`RsetePasswordCubit`, `PUT {mainApi}/profile` — the same URL as
the profile-update endpoint, declared as a local variable instead of reusing `changePasswordPath`),
`favourites` (`FavouritesCubit`, `GET /profile` re-used to read favourited cars — via
`package:http`, oddly named `favourites_services.dart`), `privacy_policy` (reads static content from
`SettingsCubit`, see `core/helpers/settings/` in §4 — not from `privacy_policy.dart`'s own
constant, which holds the hardcoded fallback text). `ProfileCubit` itself is registered
`registerFactory` but provided once globally at `bloc_providers.dart:26` (behaves as a singleton,
§5) and is also constructed fresh, screen-scoped, inside `ShellScaffold.initState()`'s
`ProfileCubit.getProfile()` call (same global instance, since `sl<ProfileCubit>()` was already
resolved once — no second instance here, just a second call into the one instance). Endpoints:
`GET /profile`, `PUT /profile` (change password path, oddly named `changePasswordPath` in
`api_path.dart` but actually just `{mainApi}/profile`), `POST /deleteAccount`. Depends on:
`auth` (`AuthStatusCubit`), `home/cash_back`, `home/complaints`.

### `home/cash_back`
Cashback balance + transaction history + apply-to-order. `CashbackScreen` (route `/cashback`, live
from Profile). `CashbackCubit` holds balance/transactions state; both its repository files
(`cashback_balance.dart`, `applycashback.dart`) use a **bare `Dio()`** per call rather than the
shared instance (§5), and `additions_screen.dart` constructs its own separate
`CashbackRemoteDataSource(Dio(), ...)` too — three independent unconfigured `Dio` instances for one
feature. Endpoints: `GET /cashback/balance`, `GET /cashback/transactions`, `POST
/cashback/apply-to-order`. No module dependencies beyond `core`.

### `home/complaints`
Single complaint form. `ComplaintScreen` (route `/complaints`, live from Profile and from
`login_noAuth.dart`). `ComplaintCubit` + `ComplaintRepository` (uses the shared `dio` correctly, one
of the few repositories here that does). Endpoint: `POST /complaints`. No dependencies.

### `home/category`
Two files, a `CategoryRemotDataSource` (`GET {mainApi}/categories`) with no cubit found anywhere
using it — see §6, could not determine a live consumer.

### `home/offers`
Offers list + detail. `OffersScreen` (route `/offers`, reached both from Home and from
`notification_router.dart`'s `offer` notification type) and `OfferDetailsScreen` (route
`/offer-details`). No dedicated cubit — `offers_service.dart` (`GET /offers`, `GET
/offers/{offerId}`) is called directly from the screen's `initState`/`FutureBuilder`-style state,
and `SearchCubit.getOffers()` (a second, separate `GET /check_for_offers` call, different endpoint,
different model) drives the home-screen offers teaser. Two different endpoints for what reads as
one concept ("offers") — see §5.

### `home/selectLanguage`
`SelectLanguage` (routes `/language` AND `/select-language` — both build the identical widget with
a different default arg; `/select-language` has zero push sites, see §3) plus `LanguageCubit`
(§4 — the app-wide locale mechanism) and `language_dialog.dart`, a smaller in-place picker used from
Settings-shaped contexts rather than the full-screen `SelectLanguage`.

### `notifications`
In-app notifications list, separate from FCM (see CLAUDE.md's Push notifications section).
`NotificationsScreen` (route `/notifications`). `NotificationsCubit` (`registerFactory`,
correctly per-screen). Endpoints (all marked `TODO(api): confirm path + method` in `api_path.dart` —
never confirmed against a real backend response, per the constants' own comments): `GET
/notifications`, `POST /notifications/read/{id}`, `POST /notifications/read-all`. Routing on tap
goes through `core/router/notification_router.dart`, the single source of truth for
notification-type → destination.

### `shell`
The 4-tab app frame (`ShellScaffold`, `ShellBottomNavBar`, `TabScrollRegistry`) — see CLAUDE.md's
App Shell section for the mechanism, which this inventory does not repeat. Also hosts
`SettingsCubit` (from `core/helpers/settings/`, not a `modules/` feature — see §4) and the
`_checkVersion()` call (`GET /settings/version`, via a **bare `Dio()`**, §5).

### `widgets` (shared, not a feature)
Reusable UI components (`CustomAppBar`, `ADGradientButton`, form fields, etc. — see CLAUDE.md's
Shared widget library section) plus two feature-shaped outliers that live here despite not being
generic: `CallUs` (`/call-us` route, reads `SettingsCubit` for contact links) and
`on_boarding/time_picker.dart` (a custom time-picker widget, not the onboarding flow).

## 2. API Inventory

Grouped by module. "Consumer" is the cubit/screen that triggers the call; "does with response"
is what happens to the parsed data. `mainApi` resolves to `productionApi_darakson` =
`https://api.daraksonksa.com/api` — **not** the `productionApi` constant one line above it in
`api_path.dart` (`https://api.darbakksa.com/api`), which is defined but unused. `oracleApi` is a
second, separate backend (`http://oracle.abudiyab-soft.com/api`) used only for loyalty points.

## 4. Shared Infrastructure

**Dio & interceptors.** One `Dio` is registered `registerLazySingleton` in `service_locator.dart:155`;
`AppInterceptors` is attached to it once, immediately after, at `service_locator.dart:156`.
`AppInterceptors.onRequest` unconditionally sets `options.baseUrl = mainApi`, a 120s send/connect
timeout, `Accept`/`Content-Type: application/json`, `Accept-Language: <langCode>`, and
`Authorization: Bearer <token>` only when a token exists (never a literal `"Bearer null"`).
**Note**: since every `api_path.dart` constant already embeds `mainApi` as a full absolute URL, and
Dio treats an absolute request path as overriding `baseUrl` entirely, the `baseUrl` assignment is
inert for nearly every real call — it only matters for the rare relative-path request. `onResponse`
and `onError` are both pass-through (`return super...`) — confirms CLAUDE.md's "no custom 401
handling" claim by direct reading, not just by that doc's word.

**`service_locator.dart` registration patterns.** `registerLazySingleton` is used for: all shared
external singletons (`Dio`, `SharedPreferencesHelper`, `DateHandler`, `PushNotificationService`),
every repository, and most remote datasources — plus three cubits that are genuinely meant to be
app-wide (`AuthStatusCubit`, `BookingCubit`, `LanguageCubit`, `SearchCubit`, `FilterCubit`).
`registerFactory` is used for the rest of the cubits (`SignInBloc`, `RegisterCubit`,
`OnBoardingCubit`, `CarsCubit`, `AdditionsCubit`, `EditProfileCubit`, `RsetePasswordCubit`,
`ForgetPasswordCubit`, `AllBookingCubit`, `ProfileCubit`, `InvoiceCubit`, `AllCarsCubit`,
`NotificationsCubit`, `LocationSelectionCubit`) — but four of these (`AdditionsCubit`,
`AllBookingCubit`, `ProfileCubit`, `InvoiceCubit`) are provided exactly once at the app root in
`bloc_providers.dart` and therefore behave as singletons in practice; see §5.

**`bloc_providers.dart` globals.** Nine providers at the `MultiBlocProvider` root:
`AuthStatusCubit`, `BookingCubit`, `LanguageCubit`, `ProfileCubit`, `AdditionsCubit`, `InvoiceCubit`,
`SearchCubit`, `AllBookingCubit`, `ThemeCubit` (the last created inline with `ThemeCubit()`, not via
`sl`, per CLAUDE.md). Everything else is resolved from `sl` closer to the screen that needs it.

**Hive boxes.** `CacheHelper` (`core/helpers/cache/cache_helper.dart`) opens exactly three boxes at
boot: `branches_box`, `cars_box`, `cache_meta_box` (TTL 5 minutes, tracked via `${key}_time` entries
in `cache_meta_box`). Of these, `cars_box` has **zero readers or writers anywhere in `lib/`** — it is
opened and never touched again (§5). `branches_box` is read/written only by
`branch_local_datasource.dart`, part of the now-orphaned `BranchRepository` chain (§5) — so
functionally dead too, though the code path to reach it still technically exists. The location
module keeps a separate, fourth Hive box (`location_cache`) of its own — not detailed here per the
task's scope.

**Localization.** Confirmed by reading `lib/language/`: `AppLocalizations` (`language/locale.dart`)
exposes `english.dart`/`arabic.dart`'s `Map<String, String>` dictionaries as getters, registered via
`AppLocalizationsDelegate` in `bloc_providers.dart`. `LanguageCubit` (`home/selectLanguage/languageCubit.dart`)
is the sole read/write path for the active locale, backed by `PreferencesConstants.lang` in
SharedPreferences (default `ar`).

**Theming.** `ThemeCubit`/`lightTheme()`/`darkTheme()` in `core/theme.dart` and `core/style/style.dart`
respectively; `AppTypography` (also in `core/style/style.dart`) is the sole text-style source.
Color tokens live in `core/constants/assets/app_colors.dart` as light/dark constant pairs plus
dynamic `*Color(BuildContext)` functions.

**Design-system helpers CLAUDE.md mandates**, confirmed present by reading: `FigmaGradientBox`
(`core/style/figma_gradient_box.dart`), the text-scale-aware `.hs()`/`.ws()`/`.sps()` extensions
(`core/helpers/text_scale_sizing.dart`), `FormValidator`/`Validate`
(`core/helpers/validation/`), `CustomAppBar`/`ADGradientButton`/`ad_prim_text_form.dart`/
`DynamicPhoneField_WithCountry.dart`/`showResponsive_Flushbar.dart` under `modules/widgets/`.

**`core/helpers/settings/`** (not a `modules/` feature, but worth noting here since it makes its
own API call and is hosted by the shell): `SettingsRepository.fetchSettings()`/`fetchSettingsSafe()`
call `GET /settings` with a **bare `Dio()`**, falling back to a hardcoded `_kFallbackSettings` object
on any failure. `SettingsCubit` (file not read in full, only its consumers) is hosted by
`ShellScaffold` per CLAUDE.md and consumed by `call_us.dart` and `privacy_policy.dart`.
